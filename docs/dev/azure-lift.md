# Lift & shift: legacy TicketDesk on an Azure VM (Round 1 azure-lift)

The legacy app (ASP.NET MVC 5 on .NET Framework 4.6.2, IIS, SQL Server 2022 Express) runs unchanged on an Azure
Windows Server 2025 VM. Terraform's `lift` stage builds the infrastructure; the **same** `ops/windows/*.ps1` scripts
that provision the local VM (`ops/onprem/provision-legacy.sh`, over ssh) provision the Azure VM through Run Command
(`ops/azure/lift.sh`). Nothing stays running: every cycle ends with the stage taken down to `none`.

Numbers: `docs/RESULTS.md` (rows "Azure lift …"), evidence `docs/evidence/azure-lift-20261108/` (index in its
`README.md`), costs `docs/dev/azure-spend.md` (rows L*).

## Decisions (the brief left these to this round)

1. **Artifacts and scripts reach the VM through a storage account read with the VM's managed identity**, not Run
   Command with a SAS. The account has shared keys disabled, so no SAS can exist; the operator uploads with
   `az … --auth-mode login` (Storage Blob Data Contributor), the VM reads `artifacts` (Reader) and writes `backups`
   and `logs` (Contributor), all container-scoped. The same account receives the backups (task 5), and there is no
   token to mint, pass on a command line or leak into Run Command history. Packages are checked on the VM against the
   SHA-256 that `lift.sh` computed: the publish package was built once on the local VM (`lift.sh fetch-publish`,
   revision `f510384`, 840 files) and its zip hash is recorded in `artifact-publish.txt`.
2. **Secrets in Key Vault, read by the managed identity**: `td-sql-sa-password` (generated by Terraform per
   environment: a restored database carries no server logins, so the Azure host needs no shared sa password),
   `td-app-admin-password` (the TicketDesk admin, used by the VM's post-provision sign-in check) and the
   `td-iis-legacy` certificate. The PFX password is used once, by Terraform's import; the VM reads the certificate's
   secret, which is a passwordless PFX with the chain. Terraform gets the two sensitive inputs as `TF_VAR_*` from
   `$TD_W/.secrets` inside the recipe shell (`scripts/tf_lift_env.sh`); they appear in no output, log or file in the
   repo (Terraform state holds them, as it already holds the VM admin password: state is outside the repo, 0600).
   The Key Vault firewall stays default-deny + home IP and now also allows `snet-vm` (service endpoint, free).
3. **Certificate from the lab CA, imported into Key Vault, installed by `Set-TdIisSite.ps1` through the managed
   identity.** The lab CA already roots the local VM's certificate, so switching clients from the local VM to Azure
   needs no new trust (the probe and the smoke test use the same `--cacert` for both); a Key Vault self-signed
   certificate would have meant a second trust anchor at the cutover. Installing with the scripts keeps one code path
   for both hosts (the KV VM extension would bind IIS differently from the local VM). The name is stable across
   rebuilds: the public IP has the DNS label `tdlab-legacy-<suffix>` (suffix = sha1(subscription/RG), as for the vault).
   **Rotation:** `TD_CERT_NAME=azure-lift ops/onprem/new-lab-cert.sh <fqdn> localhost tdlab-legacy` (new key and
   serial from the same CA) → `make azure-lift-up` (Terraform sees new file contents and imports a new certificate
   version) → `make azure-lift-provision STEPS=site+verify` (Set-TdIisSite imports the new PFX and rebinds 443 to
   the new thumbprint; the old certificate stays in the store until removed). `verify` prints the bound thumbprint.
4. **Network**: the NSG on `snet-vm` allows only 443 from the home public IP (no RDP, WinRM or SSH from anywhere);
   administration is Run Command through the control plane. The VM's own public IP gives outbound (the subnet has no
   default outbound access; no NAT Gateway). Service endpoints instead of private endpoints for Key Vault and
   storage: same "not from the internet" result at $0 instead of $0.01/h each.
5. **Updates and Defender**: `patch_mode = Manual`, automatic updates off, so Windows Update cannot reboot the VM in a
   measurement window (DECISIONS 2026-11-08). The VM lives hours and is built from the newest image version
   (October 2026 cumulative update; November's Patch Tuesday is 2026-11-10). Defender Antivirus stays on (image
   default); `verify` records its status and signature version.
6. **SQL Server cumulative update** (`ops/windows/Update-TdSqlServer.ps1`, step `sqlupdate`): the newest package on
   the CU line, KB5126934 = CU27 + October 2026 security fix (16.0.4305.5), from the Microsoft Update Catalog with
   the SHA-256 published in the KB article. Idempotent (skips at or above the target build), stops IIS while the
   instance restarts, records `@@VERSION` before/after as a `SQLUPDATE {…}` line and in `C:\TdLogs`.
7. **Backups off the VM with Put Blob through the managed identity** (`Backup-TdSite.ps1 -BlobContainerUrl`, chained
   by `Register-TdBackupTask.ps1`): SQL Express has no Agent, so Task Scheduler runs the nightly backup as before and
   each run folder (`.bak`, `site.zip` with attachments and the Lucene index, config, manifest) is copied to
   `backups/<host>/<run>/`, manifest last. Not azcopy: it would be one more binary to download and keep current, and
   PowerShell's REST call does the same for files far below the 5,000 MiB single-request limit. Not `BACKUP TO URL`:
   it only covers the database, not `site.zip`, and needs a credential object in SQL Server. Restore:
   `Get-TdBlobBackup.ps1` (downloads, checks every file against the manifest's SHA-256) + `Restore-TdSite.ps1`.
8. **Cutover with a write freeze, reads kept up**: the source database goes `READ_ONLY` (reads keep working), the
   backup moves local VM → lab-host → blob → Azure VM, the Azure host restores and passes the smoke test (which
   writes), then clients switch (the probe's base URL). A 1/s probe reads `/` and `/tickets` (signed in, a database
   read) through the whole window. Write-freeze downtime = freeze → switch; failed requests = probe failures.
   Go/no-go: if the restore or the smoke test on Azure fails, clients are not switched and the source is opened
   for writes again (rollback). A probe tick is GET `/` then GET `/tickets`, at most one tick per second (from
   lab-host one tick against Azure takes about 2 s: 0.7 s + 1.3 s over a new TLS connection each).
9. **Provisioning outside Terraform** (the vm-windows module's unused Run Command hook was removed): `terraform apply`
   builds infrastructure, `lift.sh provision` runs the steps, each timed, and individual steps can be re-run
   (`STEPS=site+verify`), like `provision-legacy.sh` on the local VM. A pipeline runs the same `make` targets.

## What the lift found (fixed in this round)

- **A backup taken under the write freeze restores read-only.** The database state is part of the backup, so the first
  cutover rehearsal's restore failed when `Restore-TdSite.ps1` mapped the pool user. The restore now opens a
  read-only restored database for writes (the restored copy is the new primary).
- **The Key Vault PFX lost its private key hours after the import.** `Set-TdIisSite.ps1` read the PFX into an
  `X509Certificate2` with `DefaultKeySet` to get the thumbprint. .NET writes such a key to a temporary container and
  deletes it on finalization; the Key Vault PFX names its key container, so the deletion removed the key that
  `Import-PfxCertificate` had just stored under the same name. Schannel kept a cached handle for a few hours, then
  failed with 0x8009030D and IIS reset every TLS connection. The script now reads with `EphemeralKeySet` (no key
  file), re-imports a certificate whose private key is unusable, and `verify` reports `private_key_usable`. The
  local VM was not affected (its OpenSSL PFX carries no container name).
- **Run Command steps use the scripts already on the VM.** A step list without `fetch` runs the previous bundle;
  `lift.sh cutover` therefore runs `fetch+restore`.
- **VM force delete left the OS disk.** With the provider's `skip_shutdown_and_force_delete` the first destroy
  waited 13 minutes and then refused to delete the resource group (the disk remained); the feature is removed.
- **Sign-in writes**: the first admin sign-in creates the admin's `UserSettings` row; reads and sign-in work on a
  `READ_ONLY` database once that row exists (tested on the Azure VM before the rehearsal).
- **Freezing with `ROLLBACK IMMEDIATE` costs a few seconds of reads**: the first rehearsal saw 12 of 322 probe reads
  fail, all on the source in the 6 s after the freeze (even the anonymous home page answers 500 while the
  connections are killed and the pool reconnects).

- **The scheduled reaper caught a real overrun.** Cycle L2's resource group outlived the agent session (usage
  limit); at 23:00Z, 7 minutes after its ttl, the reaper deleted it (done 23:04Z). Afterwards: Terraform state
  reconciled (`make azure-down` = refresh-only, then stage `none`: "No changes"), the soft-deleted vault purged (a
  recovered vault would hold the old secrets and break the next apply), the soft-deleted workspace left (not billed,
  recovered by the next foundation apply). `state-reconcile.txt`, `reaper-catch.txt`.

## Runbook

```bash
source $TD_W/.tools/env.sh; cd $TD_W/wt-azure-lift      # or the modernize checkout
make azure-reap                                          # start of session
make azure-lift-up TTL_HOURS=4                           # cert (once) + lift stage apply (ledger check first)
make azure-lift-stage SEED=1                             # scripts bundle + publish package (+ scale-S .bak)
make azure-lift-provision ARGS="RestorePrefix=seed RestoreName=baseline-s"
make azure-lift-smoke
make azure-lift-backup-drill                             # backup -> blob, loss, restore from blob, smoke
TD_LOCK_OWNER=<you> make azure-lift-cutover              # holds the VM lock: local VM -> Azure
make azure-lift-rebuild BACKUP=$TD_W/vm/exports/azure-lift/<run>   # from nothing, timed
make azure-lift-down; make azure-reap; make azure-status # end: back to "none" (Entra app only)
```

Steps of `lift.sh provision` (default = all, in this order): `fetch` (bundle + publish package from blob, SHA-256
checked) · `prereqs` (IIS + ASP.NET 4.x) · `sql` (SQL Express, sa from Key Vault) · `sqlupdate` (CU) · `site` (IIS
site, HTTPS with the Key Vault certificate) · `restore` (backup from blob) · `deploy` (publish package, host config,
first-run wizard off) · `backup-task` (nightly backup + blob copy) · `verify` (TDVERIFY JSON). Extra steps:
`backup-now`, `drill-loss`, `db-readonly`, `db-readwrite`. Output: `provision-<run>.txt` (Run Command output) and
`provision-<run>.log` (the VM's transcript, from the `logs` container).
